终于决定把博客从Hexo迁移到Hugo了

2026-10-04 10:30≈ 118字≈ 1分钟

这个博客用了很多年 Hexo。最初它简单、够用，主题也很好改。但这些年为了贴合自己的习惯，我不断加功能、改样式、补插件和脚本。回头看，网站能正常运行，却越来越依赖自己写下的那一层层“例外”。这次迁移的原因并不是 Hexo 不好，而是我改得太多，继续维护这些定制的成本开始超过它们带来的方便。

为什么决定迁移

需要维护的已经不只是文章页面。中、英、日三个站点各有配置，发布时要依次生成和部署；首页、随笔年份归档、小说分类、标签、语言切换、字数统计和关于页面，也都有各自的主题逻辑。每次想改一个小地方，都要先弄清它会不会影响另外两个语言站或其他页面。

部署流程也累积了不少历史包袱。原来的 GitHub Actions 需要为三个站点分别准备密钥、运行 Hexo，再通过脚本切换配置和生成结果。它一直能工作，但依赖版本、Node.js 运行环境和自定义脚本都需要继续照看。博客本来应该让我专心写东西，而不是每次更新都担心构建和发布流程。

所以我想把内容和展示逻辑重新理一遍，尽量回到 Hugo 已经提供的内容管理、Markdown 解析和代码高亮能力，把必须保留的个人设计放在少量清楚的模板里。

迁移是怎么做的

为了不影响正在运行的 Hexo 站，我先把 Hugo 项目放在独立目录中迁移和验证，没有直接覆盖 Hexo 项目的文件。先检查旧站的配置、主题修改、插件、文章 front matter 和 GitHub 部署流程，再以旧站生成结果作为链接和页面结构的对照基准。

文章按中文、英文、日文分别放进 Hugo 的内容目录，并尽可能保留原有标题、分类、标签、日期和文章 URL。迁移时也重新整理了内容结构：首页只列经验文章，随笔按年份归档，小说按分类归档；关于页面不套用普通文章的字数和阅读时间信息。像字数、阅读时间这样的文章数据由 Hugo 根据内容生成，新文章不需要手工补数字。

界面和 Markdown 也逐项核对。多语言切换、目录、上一页和下一页等功能迁入 Hugo 模板；代码围栏交给 Hugo 自带的 Goldmark 和 Chroma 处理。之后只需要按代码语言标注围栏，例如 sh、yaml、java 或 js，就能使用对应的语法高亮，不必为每种语言另写一套 CSS。

链接和 Google 收录会受什么影响

我把迁移前后的三份 sitemap 做了对照：中文条目数是 243 对 243，英文是 90 对 92，日文是 217 对 219。按 URL 解码和 Unicode 规范化后，已有文章地址都能找到对应项：中文 176 篇、英文 42 篇、日文 162 篇；日文 sitemap 还多列出了一篇旧站 sitemap 中没有的文章。少数地址的百分号编码等字符串表现不同，但规范化后的路径一致。

变化比较明显的是分类和标签等归档页，而不是文章正文链接。新旧站的分类路径结构、标签大小写规则有差异，因此不能只看 sitemap 总数就说所有地址完全相同。旧归档地址是否需要重定向，还要结合实际访问结果和 Search Console 数据继续确认。Google 可能需要重新抓取并更新规范网址，迁移期间收录和搜索表现也可能波动；sitemap 有助于发现网址，但不能保证页面一定收录。

接下来我会继续关注 Search Console 中的抓取、索引和 404 报告，并优先处理仍有外部链接或搜索流量的旧分类、标签地址。文章链接能够保留，是这次迁移中最重要的兼容目标之一。

之后怎么发布

Hugo 的 GitHub Actions 工作流会在 hugo-migration 分支收到推送后运行：先一次性构建三种语言，再分别把中文、英文和日文站点部署到原来的三个目标仓库。部署仍使用博客仓库中已有的三个 Actions secrets。这样以后写完文章，正常提交并推送 Hugo 分支，就会触发同一条工作流，不必手动生成三个版本。

目前迁移代码放在 hugo-migration 分支，原来的 master 仍保留 Hexo 版本。两者暂时并行，方便继续核对内容和部署结果；工作流是否成功，还要以 GitHub Actions 的实际运行记录和三个目标站点的更新情况为准。

迁移之后

这次迁移不是为了追求“换一个更时髦的工具”，而是希望减少那些只有我自己记得的特殊处理。Hugo 不会自动替我决定所有页面应该长什么样，也不是完全不需要配置；但文章、语言、模板和发布步骤现在有了更清楚的边界。以后新增内容时，我希望把精力放回写作，而不是继续给旧的定制逻辑打补丁。
